# 测试稳定性、账本归档与性能测试拆分设计

- 日期：2026-08-02
- 项目：Pensona / MultiCurrencyLedger
- 测试环境：仅 iOS Simulator，不包含真机测试
- 设计状态：已完成分段确认，待用户审核书面版本

## 1. 背景

2026-08-01 的模拟器全量测试结果如下：

- Release 模拟器构建通过。
- 单元测试 243/243 通过。
- UI 冒烟测试 9/11 通过。
- 两个交易详情相关用例因样例交易未及时出现而失败。
- 聚合运行混入性能 UI 用例后不能及时收敛和封存结果。
- 记账上下文面板的现有动效是产品主动设计，不纳入本轮缺陷整改。

本设计解决三个问题：

1. 测试样例数据初始化存在竞态，导致 UI 测试偶发找不到交易。
2. 账本服务已有空账本删除能力，但产品界面缺少安全的删除、归档和恢复流程。
3. 性能 UI 用例与日常功能测试混跑，缺少独立、可收敛、可比较的执行方式。

## 2. 已确认的产品决策

### 2.1 账本生命周期

- 空白账本允许永久删除。
- 有内容的账本不允许永久删除，只允许归档。
- 归档账本从日常账本切换器中隐藏。
- 归档账本集中显示在“管理账本 → 已归档”。
- 归档账本只读，可以查看历史数据，也可以恢复。
- 归档账本默认不计入首页资产总额和默认统计。
- 用户主动进入归档账本时，可以查看该账本自己的历史资产和统计。
- 至少保留一个未归档账本；唯一的未归档账本不能删除或归档。

### 2.2 性能测试定位

- 模拟器性能测试先输出趋势报告，不阻断普通功能测试或发布验收。
- 连续积累 3 至 5 次稳定结果后，再单独设计正式失败门槛。
- 现有记账动效保持不变；性能测试记录其表现，但不以动画持续时间较长作为失败依据。

## 3. 总体方案

采用正式的数据状态方案，分三个阶段实施：

1. 建立确定性的测试启动和样例数据就绪协议。
2. 增加持久化的账本归档状态、安全删除规则和只读保护。
3. 将日常功能测试与性能测试拆分，并生成独立趋势报告。

三个阶段保持边界独立：第一阶段不改业务数据模型；第二阶段包含数据模型迁移；第三阶段只调整测试组织和性能采集方式，不修改产品动效。

## 4. 阶段一：样例数据与 UI 测试稳定性

### 4.1 问题根因

当前 `RootTabView` 已经显示后，应用才在异步 `.task` 中依次执行默认数据和预览数据初始化。UI 测试启动应用后只能等待固定秒数，再通过“餐饮”等本地化文字寻找样例交易。这会产生两个不稳定因素：

- 页面可操作不代表样例数据已经写入完成。
- 显示文字可能因语言、分类层级或 UI 调整发生变化。

### 4.2 启动协议

新增测试专用环境变量：

- `UI_TEST_MODE=1`：启用确定性 UI 测试启动流程。
- 保留 `HOME_SAMPLE_DATA=1` 作为是否创建预览数据的开关。

在 UI 测试模式下，应用在开放根界面交互前完成：

1. 兼容数据清理。
2. 默认分类和默认账本初始化。
3. 样例账户、交易、预算、目标和提醒初始化。
4. 一次 `ModelContext.save()` 完成并通过最小数据校验。

初始化成功后，根界面暴露 accessibility identifier `app-data-ready`。初始化失败时暴露 `app-data-seed-failed`，同时提供可诊断的错误描述。生产模式不暴露这两个测试标记，也不改变现有启动体验。

### 4.3 稳定测试标识

测试不再依赖“餐饮”等显示文字定位样例交易。首页交易行根据测试样例的稳定特征暴露 identifier，例如：

- `sample-transaction-dining`
- `sample-transaction-salary`

稳定标识只用于测试定位，不进入用户数据字段，不改变备份格式。具体实现可以通过 Debug/UI 测试环境下的样例交易 UUID 集合完成。

### 4.4 幂等性与错误处理

- 相同测试数据库重复执行初始化，不得产生重复账户、钱包、交易或目标。
- 初始化完成标记只能在最终保存和最小校验成功后出现。
- 初始化失败必须让测试快速失败，不允许继续表现为“找不到某个控件”。
- 普通用户已有账户时继续遵守现有预览数据保护规则，不写入样例数据。

### 4.5 测试范围

新增或调整以下验证：

- 预览数据初始化幂等性单元测试。
- 初始化成功和失败状态测试。
- UI 冒烟测试统一先等待 `app-data-ready`。
- 交易详情和备注编辑测试使用稳定 identifier。
- 简体中文、繁体中文、英文和日文环境下不依赖显示文字定位样例交易。

### 4.6 验收标准

- UI 冒烟测试连续运行 5 次全部通过。
- 交易详情和备注编辑用例不再出现样例交易缺失。
- 重复初始化后各类样例对象数量不变。
- 测试初始化失败时，结果直接指出 seed 失败原因。
- 非测试启动不显示测试标记，也不改变生产启动流程。

## 5. 阶段二：账本归档、恢复与空账本删除

### 5.1 数据模型

在下一版 `LedgerSchema` 中为 `LedgerBook` 增加：

- `isArchived: Bool`，默认值为 `false`。
- `archivedAt: Date?`，未归档时为 `nil`。

迁移要求：

- 所有旧账本迁移后保持未归档。
- 交易数量、金额、账户余额、预算和目标数不发生变化。
- 归档状态进入当前模型、模型覆盖测试和迁移快照测试。

### 5.2 账本内容判定

由 `LedgerBookService` 提供统一的 `contentSummary` 或等价查询，不允许界面自行判断“是否为空”。内容判定至少覆盖：

- 交易、预算、储蓄目标和储蓄分配。
- 模板、周期记账、周期发生记录、分期计划和分期发生记录。
- 识别导入记录、普通导入批次和导入指纹。
- 标签、附件、交易关系、AA 分摊和结算。
- 仍带有账本作用域的兼容分类及其他账本所有对象。

全局账户和全局分类本身不构成某个账本有内容；只有明确归属于账本的数据才参与判断。

### 5.3 服务接口

`LedgerBookService` 负责以下原子操作：

- `deleteEmptyBook`：仅删除空白账本。
- `archiveBook`：仅归档有内容账本。
- `restoreBook`：恢复已归档账本。
- `contentSummary`：返回各类关联数据数量，供 UI 解释为什么只能归档。

服务必须执行以下保护：

- 唯一未归档账本不能删除或归档。
- 非空账本拒绝永久删除。
- 空白账本不需要先归档，可以直接删除。
- 已归档账本不能重复归档。
- 未归档账本不能执行恢复。
- 恢复后名称仍需满足全局唯一规则。
- 每个状态变更必须在一次保存中完成；失败时回滚。

### 5.4 只读保护

只读不能只依赖隐藏按钮。所有会向指定账本写入数据的入口必须在服务层拒绝已归档账本，包括：

- 手工新增和编辑交易。
- 导入、截图识别、URL Draft 和快捷指令。
- 模板复制、周期记账、分期计划和自动生成。
- 预算、储蓄目标、标签、附件、退款、报销和 AA 流程。

统一返回可本地化错误，例如“此账本已归档，请恢复后再修改”。读取服务允许显式查询归档账本。

### 5.5 界面流程

“管理账本”分为：

- 正在使用：只显示未归档账本。
- 已归档：显示归档时间、只读状态和恢复入口。

正常账本编辑页：

- 空白且不是唯一未归档账本时，显示红色“删除账本”。
- 有内容且不是唯一未归档账本时，显示“归档账本”。
- 唯一未归档账本显示为什么不能删除或归档。
- 删除和归档均需二次确认，确认文案明确说明是否永久删除。

归档账本详情页：

- 显示“已归档，只读”。
- 允许查看历史交易、资产和统计。
- 只提供“恢复账本”，不提供新增、编辑或删除交易入口。

如果用户归档当前账本，系统先选中另一个未归档账本，再完成归档并关闭当前编辑页面。

### 5.6 查询和统计规则

默认查询仅使用未归档账本：

- 日常账本切换器。
- 首页和当前资产汇总。
- 默认统计、计划和自动化候选。
- 新增交易的账本候选。

显式归档浏览允许：

- 仅按指定归档账本读取历史交易。
- 仅计算该归档账本自己的历史资产和统计。
- 不把归档数据混入当前汇总。

### 5.7 备份、恢复与 CloudKit

- 备份格式增加 `isArchived` 和 `archivedAt`，并提升格式版本。
- 旧备份缺少字段时按未归档处理。
- 恢复后必须保留归档状态和归档时间。
- CloudKit 编码、解码和冲突处理覆盖这两个字段。
- 如果冲突发生，以既有冲突策略处理更新时间，不引入新的静默数据删除规则。

### 5.8 测试范围

- 新模型迁移和旧备份兼容测试。
- 空账本删除成功、非空账本删除拒绝测试。
- 归档、重复归档、恢复和唯一未归档账本保护测试。
- 所有关联类型参与内容判定的覆盖测试。
- 所有写入入口拒绝归档账本测试。
- 首页、资产和默认统计排除归档账本测试。
- 显式查看归档账本历史数据测试。
- 备份恢复和 CloudKit 往返测试。
- 账本管理 UI 冒烟测试。

### 5.9 验收标准

- 空白账本可永久删除，非空账本没有永久删除路径。
- 非空账本可归档、只读查看和恢复。
- 归档与恢复前后交易数量、金额和关联对象数量一致。
- 归档账本不参与当前资产和默认统计。
- 所有非 UI 写入入口也无法修改归档账本。
- 旧数据库和旧备份升级后所有现有账本保持正常可用。
- 备份恢复与 CloudKit 同步不丢失归档状态。

## 6. 阶段三：性能测试拆分与趋势报告

### 6.1 测试计划拆分

创建两个明确的测试计划：

#### Functional

包含：

- 全部单元测试。
- UI 冒烟测试。
- 迁移、备份恢复和业务回归测试。

规则：

- 默认 Scheme 和日常 `xcodebuild test` 只运行 Functional。
- 功能测试失败会阻止验收。
- 不包含性能循环和外部 profiler 等待。
- 必须正常结束并生成完整 `.xcresult`。

#### Performance

只包含性能 UI 用例。

规则：

- 通过独立命令显式运行。
- 单模拟器、禁止 UI 测试并行克隆。
- 每条用例设置有限的 `executionTimeAllowance`。
- 崩溃、断言失败、超时或无法封存结果仍算测试失败。
- 操作耗时本阶段只记录趋势，不设发布阻断阈值。

### 6.2 外部 profiler 等待

删除每条性能用例默认执行的固定 8 秒等待。改为显式环境变量，例如：

- 未设置：立即开始自动性能测试。
- `EXTERNAL_PROFILER_WAIT_SECONDS=<n>`：仅手工 Instruments 会话按需等待。

等待只在性能测试计划生效，不能影响 Functional。

### 6.3 测量场景

独立记录：

- 冷启动和热启动。
- 月份前后切换。
- 记账页打开和关闭。
- 资产详情进入和返回。
- 统计周期及前后范围切换。
- 四个根页面滚动。

记账动效保持现有实现。趋势报告可以记录完整交互用时；只有崩溃、无法完成关闭、主线程失去响应或测试超时才作为功能性故障。

### 6.4 趋势报告

每次性能运行生成 Markdown 或 JSON 摘要，至少包含：

- 模拟器型号、系统版本、Xcode 版本和构建配置。
- 每个场景的样本数、平均耗时和最大耗时。
- 与上一次同环境结果的变化比例。
- 崩溃、超时、未收敛和运行时警告。
- `.xcresult` 和可选 Instruments trace 路径。

趋势产物写入 `.build` 下的日期目录，不纳入产品资源。前三至五次只建立基线；后续是否设置阈值需要独立评审。

### 6.5 验收标准

- 默认全量功能测试不再执行性能用例。
- Functional 能稳定完成并封存结果。
- Performance 在一个模拟器上串行运行。
- 默认运行不存在固定 8 秒 profiler 等待。
- Performance 连续运行 3 次均能正常结束并生成趋势报告。
- 功能失败与性能趋势变化在报告中明确分开。

## 7. 实施顺序与提交边界

### 7.1 第一批：测试启动稳定性

- 完成测试启动协议、就绪标记、稳定交易 identifier 和 UI 测试调整。
- 运行相关单元测试和 UI 冒烟 5 次。
- 不包含账本模型变化。

### 7.2 第二批：账本生命周期

- 先完成模型、迁移、服务和单元测试。
- 再完成查询过滤、写入保护、备份与 CloudKit。
- 最后完成管理 UI 和 UI 冒烟。
- 在此批次中重点审查数据迁移和删除保护。

### 7.3 第三批：测试计划与趋势工具

- 创建 Functional 和 Performance 测试计划。
- 调整性能用例、等待参数和串行执行方式。
- 生成三次模拟器趋势结果并核对收敛性。

每一批独立构建和测试，不混入无关 UI 重构，也不调整已确认保留的记账动效。

## 8. 完整验收矩阵

最终验收仅使用模拟器，包含：

- Debug 模拟器构建。
- Release 通用模拟器构建。
- 全部单元测试。
- Functional UI 冒烟测试连续 5 次。
- 迁移、删除保护、备份恢复和 CloudKit 编解码测试。
- Performance 独立串行运行 3 次并生成趋势报告。
- `git diff --check`。

以下内容明确不在本轮范围：

- 修改记账上下文面板动效。
- 真机性能结论。
- 账本回收站、延迟删除或批量合并账本。
- 根据首轮趋势结果立即设定发布阻断阈值。
