# iCost 功能等价补全总设计

日期：2026-07-13
状态：已确认
目标版本基线：本机 iCost 4.6.2，以及 2026-07-13 中国区 App Store 中 iCost 4.6.3 的公开功能说明

## 1. 目标

在 `MultiCurrencyLedger` 现有架构、数据和视觉语言上补齐 iCost 已公开的记账能力。已有能力保留；若现有账务口径不完整，则以更严格、可追溯且可测试的规则替换。功能等价不等于复制 iCost 的页面、图标、素材或布局。

本路线图覆盖：核心记账、二级分类、标签、图片附件、模板、退款、报销、组合付款、批量操作、周期、分期、URL Scheme、资产、统计、日历、预算、存钱、多币种、数据导入导出与恢复、iCloud 同步、隐私保护、秒开模式、截图/文本/语音智能记账，以及账单小票/分享能力。

小组件与位置附件明确延后，不属于本轮完成标准。

## 2. 已确认的产品原则

1. 保留当前多账本、多币种账务内核和现有玻璃卡片视觉体系。
2. 只复刻功能，不复刻 iCost UI。
3. 所有记账入口共享同一套校验、余额、预算和统计规则。
4. 优先保证历史数据、余额和账本隔离正确，再增加可见功能。
5. 采用五阶段增量交付，每阶段形成可使用、可测试、可回滚的闭环。
6. 非必要不启动 Simulator；只有阶段性 UI、系统跳转或最终回归无法由其他验证替代时才使用。

## 4. 总体架构

### 4.1 统一交易草稿

新增 `TransactionDraft` 作为全部输入入口的唯一中间表示。手工新增、编辑、复制、模板、退款、报销、周期、分期、截图、文本、语音和 URL Scheme 都只能创建草稿，不能各自在界面层拼装交易或修改余额。

草稿提交固定经过：

```text
输入入口
  → TransactionDraft
  → TransactionValidator
  → WalletImpactEngine
  → TransactionCommitService
  → SwiftData 保存
  → 资产 / 预算 / 统计按流水刷新
```

### 4.2 钱包影响计算

`WalletImpactEngine` 是纯计算组件，输入规范草稿或既有交易，输出 `[WalletDelta]`。每个 `WalletDelta` 只表达钱包 ID、币种和正负变动。

- 支出：来源钱包减少实付金额及适用手续费。
- 收入：目标钱包增加实收金额。
- 转账：来源减少、目标增加；本金不计收支，手续费计支出。
- 换汇：来源减少、目标增加；本金不计收支，手续费计支出。
- 调整：按方向增减指定钱包，不伪装为收入或支出。
- 组合付款：每个付款明细分别减少对应钱包，总和必须等于实付金额。
- 退款：退款钱包增加，但统计冲减关联原消费，不作为普通收入。
- 报销入账：收款钱包增加，并冲减关联交易的个人承担额。

新增、替换、删除和批量操作必须在单个提交边界中反算旧影响、应用新影响并保存。任一步失败时恢复交易与钱包快照。

### 4.3 兼容现有交易

现有 `LedgerTransaction` 保留为交易头。单钱包旧交易继续通过已有来源/目标字段读取；新增组合付款使用付款明细关系。领域适配器把新旧两种存储表示转换为同一组 `WalletDelta`，避免强制一次性重写全部历史流水。

资产、预算和统计不持有独立业务余额缓存。钱包当前余额是提交性能缓存，但必须可以从期初余额与已提交流水重新计算、核对和修复。

### 4.4 清晰组件边界

- `LedgerScope`：账本、月份和本位币范围，不访问 SwiftData。
- `TransactionDraft`：表达用户意图，不修改模型。
- `TransactionValidator`：字段、归属、币种、关联关系和金额校验。
- `WalletImpactEngine`：纯函数计算钱包影响。
- `TransactionCommitService`：唯一交易写入边界。
- `TransactionQueryState`：组合搜索和排序纯状态。
- `BudgetAnalyticsService`：统一预算口径。
- `LedgerAnalyticsService`：日历、趋势、分类和环比统计。
- `LedgerIntegrityService`：余额重算和账务差异检查。
- `ImportCoordinator`：解析、映射、预览、去重、提交和撤销。
- `SyncCoordinator`：CloudKit 记录、删除标记、冲突和同步状态。
- `AppLockCoordinator`：Keychain、LocalAuthentication 和隐私遮罩。

## 5. 功能数据语义

### 5.1 分类与标签

分类支持最多两级。子分类必须与父分类同为支出或收入类型。分类可以限制在指定账本使用；归档分类保留历史引用但不出现在新交易候选中。

标签是账本范围内的独立实体，一笔交易可关联多个标签。标签参与搜索、统计和批量修改，但不改变余额或预算归类。

### 5.2 组合付款

组合付款只适用于支出和退款去向等明确场景。每个付款明细包含钱包、金额和顺序。所有金额为正数且币种必须与交易计价币种一致；首版不在一笔组合付款中隐式换汇。付款明细总和必须严格等于实付金额。

### 5.3 退款

退款必须关联原支出，允许多次部分退款。累计有效退款不得超过原交易实付金额。删除或修改退款时重新检查累计值。退款在现金流中表现为钱包流入，在消费统计和预算中冲减原支出的分类、账本和原消费月份；另提供按退款实际发生月份查看现金流的维度。

### 5.4 报销

支出可标记为不报销、待报销、部分报销或已报销。一次报销入账可以关联一笔或多笔待报销支出，但每笔累计报销不得超过可报销金额。

- 原支出仍保留真实付款与分类。
- 报销入账增加收款钱包。
- 普通支出统计可同时展示总消费和个人承担额。
- 预算默认按个人承担额计算，并提供按原始支出查看的说明入口。

### 5.5 图片附件

原图保存在 App 沙盒 `Application Support` 下，SwiftData 只保存相对路径、类型、尺寸、校验值和创建时间。生成受控缩略图；删除交易时按引用计数清理文件。备份时附件进入备份包，恢复时校验文件完整性。

### 5.6 模板、周期和分期

模板保存草稿快照，不保存余额结果。使用时重新校验已归档账户、失效分类、标签和币种。

周期账单包含频率、下次日期、结束条件、自动保存策略和模板。默认生成待确认草稿；只有用户明确开启且草稿满足安全策略时才自动提交。

消费分期关联原消费；账单分期关联信用账户账单。计划保存本金、手续费、期数、首期日期和生成记录。每一期拥有稳定幂等键，避免重启、迁移或同步后重复生成。

### 5.7 存钱计划

存钱目标与真实交易分离。目标包含名称、目标金额、币种、目标日期、模式、状态和显示属性；投入/取出产生目标分配记录，不改变钱包余额、资产总额、收入、支出或预算。

支持灵活存钱、定额计划与打卡。关联账户仅用于说明资金位置，不锁定余额。若已分配总额高于可参考资产，显示警告但不自动修改账务。

## 6. 导入、备份与同步

### 6.1 导入流水线

导入文件先解析到暂存区，经过字段映射、账户/分类匹配、币种校验、重复指纹和用户预览后，再转换为普通 `TransactionDraft` 批量提交。

提供支付宝、微信、云闪付和 iCost 等常见预设；同时提供自定义 CSV/XLSX 列映射，以覆盖其他平台。每次导入保存批次 ID、来源、成功/跳过/失败数量和创建的交易 ID，并支持整批撤销。

### 6.2 备份与恢复

JSON 备份升级为带版本、清单和文件校验值的完整备份包，包含模型数据、设置和图片附件。恢复前先验证版本、完整性和冲突策略，并展示覆盖或合并预览。CSV/XLSX 用于交换，不承担无损恢复承诺。

### 6.3 iCloud

默认仅本地保存。用户主动开启后，由 `SyncCoordinator` 同步到 CloudKit 私有数据库。同步对象使用稳定 UUID、更新时间、设备来源和删除标记；不同设备修改同一对象时保留较新版本，并保存可查看的冲突副本。

钱包缓存余额不作为可信同步源。合并流水后由 `LedgerIntegrityService` 重新计算余额。同步页显示网络、iCloud、最近同步、待处理记录、冲突和错误状态。

## 7. 安全与外部入口

### 7.1 App 锁

数字密码只以 Keychain 中的加盐派生校验值保存。Face ID/Touch ID 使用 `LocalAuthentication`。进入后台或系统截屏切换状态时使用隐私遮罩。连续失败采用本地渐进等待，不删除账务数据。

### 7.2 URL Scheme

注册本项目独立协议 `multiledger://`，不复用 `icost://`。第一版支持：

```text
multiledger://entry?type=expense&amount=28.50&currency=CNY&note=午餐
```

解析器只接受白名单字段，限制字符串长度，严格解析金额和日期，拒绝未知币种、无效 UUID、跨账本账户和不支持的交易组合。链接只能打开待确认草稿，不允许直接入账；密码、令牌和敏感同步信息不得出现在 URL 中。

### 7.3 智能记账

截图、文本和语音经过同一识别响应、候选归一化、账户匹配和安全评估流程。低置信度、转账/换汇、正手续费、未来日期、未知分类、账户歧义和金额关系异常必须人工确认。自动入账始终是显式的用户设置，而不是默认行为。

## 8. 导航与交互

继续使用当前底部“账本、资产、存钱、记一笔”，不复制 iCost 五标签结构。

- 账本首页顶部提供搜索和统计入口。
- 月历与现有月份切换共用同一 `LedgerScope`。
- 设置按记账规则、分类与标签、自动化、数据与同步、安全与外观分组。
- 记账页默认只展示快速路径；标签、报销、图片、组合付款、周期和分期放入更多选项。
- 搜索、统计、预算和资产视图均可下钻到带条件的交易列表。
- 模板、URL Scheme、截图、文本和语音共用同一确认页。
- 错误页面提供可执行修复入口，不静默忽略归档账户、缺失汇率或异常计划。

## 9. 错误处理

领域错误使用可测试、可本地化的错误枚举，至少区分：无效金额、钱包归属错误、币种不匹配、余额警告、组合付款不平、退款超额、报销超额、分期参数错误、重复计划生成、无效外部链接、导入重复、备份损坏、同步冲突和认证失败。

余额不足沿用当前“明确警告后允许继续”的产品语义，但信用/负债账户按账户类型显示正确文案。任何原子提交失败都恢复模型与钱包快照。批量操作先全量校验；若无法保证整批原子性，则不提交任何记录。

## 10. 迁移策略

1. 引入版本化 SwiftData Schema 和显式迁移计划。
2. 不以删除本地数据库作为开发或发布迁移方案。
3. 新字段提供兼容默认值；新关系允许旧数据为空。
4. 旧单钱包交易由兼容适配器读取，新组合付款使用明细关系。
5. 分类迁移为一级分类；只有用户创建子分类后才形成二级结构。
6. 迁移后运行只读一致性检查并展示差异，不自动改余额。
7. 有历史流水的账本、账户、钱包、分类和标签优先归档，不物理删除。

## 12. 测试与验证

### 12.1 自动化覆盖

- `WalletImpactEngine` 覆盖所有交易类型、手续费、组合付款、退款和报销。
- 新增、替换、删除和批量操作覆盖成功及每个失败回滚点。
- 账本、月份、币种、分类、标签、退款和报销统计口径保持一致。
- 周期和分期在重启、重复触发、迁移和同步后保持幂等。
- URL Scheme 覆盖白名单、边界长度、非法数值、未知引用和跨账本攻击输入。
- 导入覆盖列映射、重复指纹、部分错误、整批撤销和附件恢复。
- 同步覆盖创建、更新、删除、离线重试和冲突副本。
- 迁移使用旧版本数据库夹具验证无数据丢失。
- 大量流水下验证搜索、月历和统计不在主线程重复做高成本工作。

### 12.2 Simulator 原则

日常优先静态编译、纯逻辑测试和内存数据库测试，不为每个小改动启动 Simulator。只有 SwiftUI 导航、URL Scheme/App Intent 跳转、系统权限或阶段性最终回归无法由其他方式验证时才启动。iCloud 与生物识别先通过协议和测试替身验证逻辑，最后进行必要的设备验证。

## 13. 总体验收标准

1. 现有账本、账户、钱包、交易、预算和识别记录在迁移后仍可用。
2. 所有交易入口共享统一草稿、校验、钱包影响和提交服务。
3. 任意新增、编辑、删除、退款、报销、分期或批量操作后，余额、资产、预算和统计一致。
4. 组合付款总额、退款上限、报销上限、周期/分期幂等和账本隔离均有自动化测试。
5. 除小组件与位置附件外，本设计功能矩阵中的目标均有可使用入口，不以占位页作为完成。
6. 新界面遵循本项目视觉语言，不复制 iCost 的页面、素材或布局。
7. 非必要不运行 Simulator；所有完成声明均提供与风险相称的验证证据。
