# 截图自动记账纵向闭环设计

日期：2026-07-11  
状态：已通过对话确认，等待书面审阅

## 1. 背景与决策

当前项目已经具备一套可工作的 SwiftUI、SwiftData 记账底座，包括多账本、账户、多币种钱包、收入、支出、同币种转账、换汇、余额调整、月度预算、本位币折算、分类、筛选和导出。现阶段的主要问题不是页面完成度，而是用户仍需手工填写交易，产品尚未形成足够鲜明且可持续使用的核心价值。

产品定位确定为：

> 面向日常记账用户，通过系统级快捷指令截取支付结果，由 AI 识别并自动入账；同时原生支持同一账户下的多币种钱包。

日常记账是核心使用循环，截图自动入账是降低摩擦的主要卖点，多币种账户模型是长期差异化能力。

下一阶段采用“自动记账纵向闭环”路线。暂停非核心 UI 精修、存钱模块和复杂统计，优先验证截图识别能否让用户稳定、准确地完成每日记账。

## 2. 成功标准

第一阶段的主指标是：至少 70% 的真实截图可以直接正确入账，无需用户修改。

质量护栏如下：

- 自动入账中的金额与币种准确率不低于 99%。
- 自动入账后需要修改账户或分类的比例低于 2%。
- 同一截图或同一笔交易的重复触发不得生成重复流水。
- 从触发快捷指令到成功震动的中位耗时不超过 8 秒。
- OCR、网络、模型、解析或持久化失败不得改变钱包余额。
- 原始截图不得被默认写入长期存储、分析日志或识别历史。

这些指标通过小范围真实测试统计。没有通过质量护栏的结果必须降级为人工确认，不能为了提高自动入账覆盖率而降低财务数据可靠性。

## 3. 参考实现结论

设计参考了本机“iCost - V3.7.1”快捷指令的实际流程。应继承其产品逻辑，而不是复制其超长快捷指令实现。

值得继承的逻辑包括：

- 识别前从 App 获取真实账本、账户、分类和标签候选。
- 截图先裁掉时间、电量等系统区域，再在本地进行 OCR。
- 只把 OCR 文本、候选列表和用户规则发送给模型。
- 模型返回结构化的 `results` 数组，允许一张截图包含多笔交易。
- 模型返回的账户和分类必须与候选名称完全一致。
- 账户按完整名称、卡号尾号、银行简称依次匹配。
- 普通收支、退款、转账、充值、还款和投资资金移动使用不同语义。
- 原价、优惠、手续费分别识别。
- 无法匹配账户或分类时要求用户选择。
- 模型响应需要兼容 Markdown 代码块并进行严格 JSON 校验。

不在第一版照搬的内容包括：

- 在快捷指令中维护多个模型服务商、API 地址和密钥。
- VPN 自动连接和断开。
- 在快捷指令中维护完整编辑菜单。
- 让用户维护大段 Prompt。
- 标签、报销状态、不计预算等高级选项。
- 成功通知或独立通知快捷指令。

## 4. 用户体验流程

### 4.1 首次设置

1. 用户在 App 的“快捷记账设置”中安装或更新官方快捷指令。
2. App 提供 Action 按键、轻点背面和 AssistiveTouch 的配置说明。
3. 用户授权 App 对支付截图进行本地 OCR，并将识别后的交易文字、账户候选和分类候选发送给云端 AI。
4. 用户选择默认账本。
5. 用户决定是否开启高置信度自动入账，以及是否允许收入自动入账。

### 4.2 日常自动入账

1. 用户停留在支付成功页或交易详情页。
2. 用户通过 Action 按键、轻点背面或 AssistiveTouch 启动同一个快捷指令。
3. 快捷指令截图，并将图片交给 App 提供的 App Intent。
4. App 裁剪系统区域，并通过 Apple Vision 在本地提取文字。
5. App 获取当前账本中的账户、币种钱包和分类候选。
6. App 将 OCR 文本、必要候选和识别规则发送给识别 API。
7. App 对返回结果执行结构校验、金额校验、账户与钱包匹配、币种冲突检查和重复检测。
8. 通过全部自动入账门槛的结果由现有 `LedgerService` 写入。
9. App Intent 向快捷指令返回成功，快捷指令触发一次震动并结束。

成功后不发送本地通知，也不强制打开 App。

### 4.3 需要确认

出现以下情况时打开 App 的轻量确认页：

- 首次出现某个支付渠道、银行或银行卡尾号。
- 无法精确匹配具体账户或币种钱包。
- 分类不可靠。
- 截图同时出现原价、优惠、手续费等多个候选金额且关系不一致。
- 币种与账户钱包冲突。
- 疑似重复但无法完全判定。
- 交易属于转账、换汇、退款、信用卡还款、充值、投资资金移动或其他复杂类型。
- 一张截图包含多笔交易，其中至少一笔不能安全自动入账。

用户确认保存后，App Intent 返回成功并触发震动。

### 4.4 失败

- 网络超时：不创建流水，快捷指令显示“识别超时，请重试”。
- OCR 为空：不调用模型，快捷指令提示无法读取交易信息。
- API 限流或服务错误：不创建流水，保留不含截图的失败摘要。
- 无效 JSON 或缺少必要字段：不创建流水，允许重试或手动记账。
- 重复交易：不再次写入，显示“该交易可能已记录”。
- 持久化失败：交易与余额变更整体回滚。

失败时不震动，避免用户误认为已经入账。

## 5. 系统架构

### 5.1 薄快捷指令

官方快捷指令只承担四项职责：

1. 截取当前屏幕。
2. 将截图传给“识别并记账”App Intent。
3. 在 App Intent 要求确认时打开 App。
4. 成功时震动一次，失败时显示简短错误。

Action 按键、轻点背面和 AssistiveTouch 只是同一快捷指令的不同触发入口，不产生三套业务逻辑。

### 5.2 App Intent

App Intent 是快捷指令与 App 内部识别系统的唯一接口，负责：

- 接收截图和生成请求标识。
- 调用截图预处理与本地 OCR。
- 调用识别协调器。
- 返回成功、需要确认、重复或失败状态。
- 在成功状态下向快捷指令提供可触发震动的结果。

App Intent 不直接修改钱包余额，也不包含 Prompt、账户匹配和交易类型判断规则。

### 5.3 本地 OCR 与预处理

- 自动裁剪状态栏等系统区域。
- 使用 Apple Vision 提取文本和文本位置。
- 保留用于交叉验证的原始 OCR 文本，但不把原始截图持久化。
- OCR 完成或请求结束后释放图片数据。
- 对明显为空、过小或无法识别的截图提前失败。

### 5.4 识别 API 网关

使用一个薄服务端网关保护模型密钥、统一请求结构、执行速率限制和校验模型响应。网关不保存用户账本，也不直接创建交易。

网关接收：

- OCR 文本。
- 账户和币种钱包候选的最小必要信息。
- 分类候选。
- 当前日期、默认币种和必要识别规则。

网关返回经过结构校验的候选交易数组。请求日志不得记录完整 OCR 文本、账户全名或模型密钥。第一版固定一个受控模型服务，不向普通用户暴露服务商、URL、Prompt 或 API 密钥。

### 5.5 识别协调器

识别协调器在本地拥有最终决策权，负责：

- 校验 API 结构和字段类型。
- 交叉检查 OCR 文本与模型输出。
- 计算金额关系。
- 匹配账本、账户和钱包。
- 执行重复检测。
- 判断自动入账、人工确认或失败。
- 调用 `LedgerService` 创建正式流水。

模型只能提出候选，不能直接修改 SwiftData 或钱包余额。

### 5.6 账户映射规则

保存类似以下确定性映射：

```text
支付宝 + 招商银行 + 尾号 1234 + CNY
→ 日常账本 / 招商银行账户 / CNY 钱包
```

匹配顺序为：

1. 用户已经确认并保存的支付渠道、银行、尾号和币种映射。
2. 完整账户名称。
3. 银行或支付渠道与卡号尾号。
4. 银行简称与币种。
5. 无法确定时要求选择。

用户在确认页修正账户后，App 询问是否保存映射。映射规则可以在设置中查看和删除。币种与目标钱包不一致时禁止自动入账。

## 6. 识别数据契约

API 返回一个或多个候选交易。每条候选至少包含：

- `type`：`expense`、`income`、`transfer`、`exchange`、`refund` 或 `unknown`。
- `paidAmount`：实际支付、收到或移动的金额。
- `originalAmount`：优惠前金额，可为空。
- `discountAmount`：优惠金额，默认为零。
- `feeAmount`：手续费，默认为零。
- `currencyCode`：ISO 4217 货币代码。
- `date` 和 `time`。
- `merchantOrCounterparty`。
- `sourceAccountHint` 和 `destinationAccountHint`。
- `categoryCandidate`。
- `note`。
- 每个字段的置信度。
- 支持自动判断的简短证据摘要。

模型返回的账户和分类名称必须来自请求候选。返回未知候选时使用明确的空值，不允许创造不存在的账户、钱包或分类。

原始模型响应可先去除 Markdown 代码围栏，但去除后仍必须通过严格 JSON Schema 校验。缺少必要字段或出现不支持的枚举值时整体降级，不能容错猜测。

## 7. 金额和账务语义

余额与收支统计必须以实际资金变化为准：

- `paidAmount` 是修改钱包余额和收支统计的唯一主金额。
- `originalAmount` 只用于交易详情。
- `discountAmount` 不单独修改余额。
- `feeAmount` 按现有手续费逻辑产生额外支出。
- 存在原价和优惠时，应满足 `originalAmount - discountAmount ≈ paidAmount`；不满足时要求确认。

例如原价 CNY 100、优惠 CNY 15、实付 CNY 85：钱包余额减少 CNY 85，月度支出增加 CNY 85，详情展示原价和优惠。

不同交易类型的处理如下：

- 普通消费：高置信度时可自动创建支出。
- 明确收款或工资：用户允许收入自动入账且高置信度时可创建收入。
- 同币种自有账户移动：进入确认，使用现有 `transfer`。
- 两种币种之间的换汇：必须得到换出和换入两个金额，进入确认并使用现有 `exchange`。
- 退款：第一版识别并预填，但不静默当作普通收入。后续增加与原支出关联的退款语义。
- 信用卡还款、充值和投资资金移动：识别为转账候选，必须确认两端账户。
- 一张截图包含多笔交易：拆分候选后逐笔判断；无法安全批量自动入账时进入确认。

## 8. 自动入账门槛

只有同时满足以下条件才允许自动入账：

- 类型明确为普通支出，或为用户已允许自动记录的普通收入。
- `paidAmount` 为正数，金额和币种格式有效。
- OCR 原文与模型结果能互相印证。
- 日期和时间合理，不是明显的未来交易。
- 账户线索精确命中现有账本、账户和币种钱包。
- 分类来自当前分类候选，并达到可接受置信度。
- 没有命中截图指纹或交易特征重复。
- 没有退款、撤销、处理中、失败等风险状态词。
- 不属于转账、换汇、还款、充值、投资资金移动或多金额歧义场景。

具体置信度阈值必须可配置，并通过真实样本校准。不得只相信模型自报的整体分数。

## 9. 本地数据模型

### 9.1 LedgerTransaction 增量字段

为现有 `LedgerTransaction` 增加以下可选信息：

- 商户或交易对象。
- 原价。
- 优惠金额。
- 自动识别来源。
- 识别记录关联。

这些字段不改变现有流水驱动余额的原则。标签、二级分类、报销状态和“不计预算”暂不纳入本阶段。

### 9.2 ImportRecord

记录一次识别请求的可审计摘要：

- 本地请求标识。
- 截图内容指纹，不保存图片。
- 归一化交易特征指纹。
- 创建时间。
- 状态：处理中、已自动入账、待确认、失败、疑似重复、已撤销。
- 结构化识别摘要。
- 字段置信度。
- 自动入账或降级原因。
- 最终交易关联。

### 9.3 AccountMappingRule

保存支付渠道、银行、尾号、币种与目标账本、账户、钱包之间的映射。规则包含创建时间、最近使用时间和是否由用户明确确认。

## 10. 必要界面

### 10.1 快捷记账设置

- 安装或更新官方快捷指令。
- Action 按键、轻点背面和 AssistiveTouch 配置说明。
- 截图与 AI 数据处理授权。
- 默认账本。
- 高置信度自动入账开关。
- 收入自动入账开关。
- 识别服务状态。
- 测试一次截图识别。

### 10.2 识别确认页

按重要性展示交易类型、实付金额、币种、账户、分类、商户、时间、备注、原价、优惠和手续费。AI 不确定或冲突的字段需要突出显示，可靠字段保持较低视觉权重。

### 10.3 识别记录

展示最近的已自动入账、待确认、失败、疑似重复和已撤销记录。每条记录可以查看识别摘要、最终流水和决策原因，但不能查看已经删除的原始截图。

### 10.4 账户映射管理

允许用户查看、删除和重新建立账户映射。确认页修正账户时，默认询问是否记住本次映射。

### 10.5 现有界面最小变化

- 交易详情增加“截图识别”来源、原价和优惠信息。
- 自动流水继续出现在现有首页、交易列表和资产页。
- 不建立独立于正式账本的自动流水系统。
- 当前“存钱”占位模块暂不继续开发。

## 11. 重复检测与事务安全

重复检测使用两层依据：

1. 截图内容指纹，用于拦截完全相同截图。
2. 归一化交易特征，用金额、币种、时间、商户和账户线索识别同一交易的不同截图。

完全匹配时直接阻止写入；相似但不确定时进入确认页。重复窗口和相似度阈值必须可调整，并通过测试样本校准。

正式入账必须通过现有 `LedgerService`。创建交易、修改钱包余额和关联 `ImportRecord` 应当作为一个可回滚操作处理。任何一步失败都不得留下孤立流水或错误余额。

## 12. 隐私和安全

- 首次使用前明确说明发送给模型的数据范围。
- 默认仅发送本地 OCR 文本和最小必要候选，不发送完整截图。
- 原始截图不得长期保存，也不得进入分析和错误日志。
- 服务端日志不得记录完整 OCR 文本、账户全名或请求中的敏感字段。
- 模型密钥只存在于受控服务端，不写入 App 或快捷指令。
- 传输必须使用 TLS。
- 网关不使用用户交易内容训练模型，并且只选择明确承诺 API 数据不用于训练的模型服务。
- 用户可以关闭自动记账并清除识别记录和账户映射。

## 13. 测试设计

### 13.1 单元测试

- JSON Schema 校验和 Markdown 代码围栏清理。
- 必填字段、枚举、金额和币种校验。
- 原价、优惠、实付金额关系。
- 账户完整名称、尾号、银行简称和币种钱包匹配。
- 同图指纹和相似交易重复检测。
- 支出、收入、转账、换汇及手续费对余额的影响。
- 入账失败时的完整回滚。
- JPY 等零小数币种和常用两位小数币种。

### 13.2 集成测试

- Apple Vision OCR 的空结果、多区域文字和状态栏裁剪。
- 模拟 API 正常、超时、限流、无效 JSON 和缺少字段。
- App Intent 的成功、确认、重复和失败返回。
- 一张截图包含多笔交易。
- 用户修正账户后创建映射，下一次自动命中。
- 原始截图在所有结束路径中都被释放且未写入持久化存储。

### 13.3 端到端测试

- Action 按键等价入口由同一快捷指令触发。
- 支付截图到自动入账，再到首页和账户余额更新。
- 需要确认的截图打开正确页面，确认后保存并震动。
- 网络失败不震动、不创建流水、不改变余额。
- 连续触发同一截图不会重复入账。

### 13.4 真实样本验证

建立经过脱敏的测试集，覆盖微信、支付宝、银行 App、Apple Pay、外币消费、收入、退款、转账、换汇和多笔交易。样本只在取得明确授权后用于测试，并优先保存脱敏 OCR 文本与期望结构，而不是原始截图。

## 14. 实施顺序

1. 冻结非核心 UI 和“存钱”模块。
2. 建立脱敏截图与期望结果测试集。
3. 实现截图预处理、本地 OCR 和结构化识别实验。
4. 定义并验证识别数据契约。
5. 实现 `ImportRecord`、账户映射和重复检测。
6. 将识别协调器接入现有 `LedgerService`。
7. 实现轻量确认页、识别记录和账户映射管理。
8. 实现最薄 App Intent 和官方快捷指令。
9. 用少量用户进行两周真实测试。
10. 根据高频失败样本迭代，直到达到自动入账和质量指标。

## 15. 明确不在本阶段实施

- 全 App 视觉重构。
- 存钱目标和自动转入。
- 银行流水同步。
- 完全本地大模型。
- 用户自选模型服务商。
- 用户自带 API Key。
- 用户维护大段自定义 Prompt。
- 复杂消费分析和增长功能。
- 标签、二级分类、报销和“不计预算”。
- 针对每个支付 App 单独维护完整模板系统。
- 无人工兜底的完全静默导入。

## 16. 后续决策点

只有在真实测试表明其必要时，才考虑以下扩展：

- 结构化的“我的识别习惯”规则。
- 商户到分类的本地学习规则。
- 与原支出关联的退款模型。
- 二级分类和标签。
- 针对高频失败页面的轻量解析规则。
- 自动汇率更新及截图交易的历史汇率保存。
- 将主导航中的“存钱”替换为统计或自动记账入口。
