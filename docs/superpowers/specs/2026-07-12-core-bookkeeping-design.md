# 核心记账闭环设计

日期：2026-07-12  
状态：待书面审阅

## 1. 目标与边界

本阶段只完善 App 内的日常记账闭环：用户能在正确的账本与月份范围内录入、查找、修正、复制和删除交易；任何操作后，钱包余额、首页汇总和预算数据都保持一致。

本阶段不开发快捷指令、截图识别、AI 服务、存钱目标、复杂统计或投资分析。快捷指令以后只能调用本阶段稳定下来的交易草稿与入账能力，不能拥有独立账务规则。

## 2. 现状与待修复问题

项目已有多账本、多币种钱包、五种交易类型（支出、收入、转账、换汇、余额调整）、交易详情、基础编辑、筛选和月度预算。

当前存在的关键断点：

- `TransactionListView` 未按当前账本筛选，可能显示其他账本交易。
- 首页的月度概览和预算固定使用当前月，而记录区域可切换月份，导致同页数据范围不一致。
- 交易编辑只能更改金额、日期、备注和部分手续费，无法修正账户、钱包、类型、分类或商户。
- 明细页缺少关键词检索、任意日期范围和金额范围；用户难以找到旧交易。
- 手工录入没有商户字段，也没有对常用选择的轻量复用。

## 3. 范围与优先级

### P0：统一数据范围与账务正确性

所有交易读取和统计统一由以下范围确定：

```text
selectedBookID + selectedMonth（若页面按月展示） + baseCurrencyCode（仅折算/预算）
```

- 首页月度概览、预算卡片、每日记录卡使用同一个 `selectedMonth`，而不是 `.now`。
- 预算编辑和读取使用当前选中的账本、月份与本位币。
- 明细页默认限制为当前账本；筛选面板可改为“全部账本”，但默认值必须是当前账本。
- 账户、分类、钱包候选均限定在当前账本和当前可用状态。
- 每次新增、替换或删除交易后，钱包余额、月度汇总和预算进度以同一批流水重新计算，不在界面层维护独立余额缓存。

### P1：完整且安全的交易编辑

编辑页须复用录入页的字段与校验规则，并允许修改：

- 类型、金额、日期、备注、商户/交易对象、分类。
- 来源与目标账户/钱包；转账与换汇的目标金额；适用时的手续费。

保存采用单一服务操作：验证新草稿 → 回滚旧交易对钱包造成的影响 → 以新草稿记账 → 保存 SwiftData。任一步失败必须回滚到原交易和原余额；界面不得直接改钱包余额。

编辑类型变化时，移除不适用字段：例如支出不保留目标钱包，非转账/换汇不保留手续费；换汇必须仍有两个不同币种的钱包及两个正数金额。

### P1：可检索的交易明细

明细页新增以下本地筛选能力：

- 关键词：匹配商户/交易对象、备注、分类和账户名；忽略大小写及首尾空白。
- 时间：保留快捷范围（全部、本月、近 30 天、今年），另支持起止日期的自定义范围。
- 金额：最小值、最大值，按交易的主金额匹配；转账/换汇使用来源金额。
- 既有条件：账本、账户、币种、类型、分类。
- 排序：日期倒序（默认）、日期正序、金额从高到低、金额从低到高。

筛选状态在明细页顶部以简短摘要呈现，并提供一次性清除。无结果页面须说明当前限制条件；不会因搜索而改变账本数据。

### P1：更快的手工录入

录入表单新增“商户或交易对象”字段，写入 `LedgerTransaction.merchantOrCounterparty`。

在本地偏好中按账本记录最近一次成功保存的交易类型、来源钱包和对应类型的分类。打开录入页时仅将它们作为默认值；钱包或分类已删除、停用、跨账本或与交易类型不匹配时自动回退到第一个合法候选，不创建隐式数据。

保存成功后清空金额、商户、备注和类型专属临时字段，但保留当前账本及最近合法的账户/分类选择，以支持连续录入。提供“复制为新交易”入口：从详情页带入原交易的类型、钱包、分类、商户和备注，日期默认为现在、金额需由用户确认。

## 4. 组件和接口

### 4.1 范围解析

新增轻量的 `LedgerScope`（或同等纯值类型）集中表达账本、月份和本位币，供首页、明细页和预算查询构造条件。它不访问 SwiftData，不持有 View 状态。

### 4.2 交易草稿与提交服务

将录入和编辑共同字段收敛为 `TransactionDraft`。草稿负责表达用户输入，不修改模型。

`LedgerService` 或与其相邻的提交服务负责：

1. 验证类型、钱包归属、币种、金额和手续费。
2. 将草稿创建为规范 `LedgerTransaction`。
3. 新建、替换、删除时原子更新流水和关联钱包余额。

录入页、编辑页和复制入口都只创建草稿并调用服务；不得各自拼装余额变动逻辑。

### 4.3 明细查询状态

使用 `TransactionQueryState`（或等价值类型）保存所有筛选和排序条件。过滤与排序为可测试的纯函数：输入交易集合和查询状态，输出显示顺序。SwiftUI 仅负责显示与编辑该状态。

## 5. 错误处理与迁移

- 无效金额、日期范围倒置、无匹配钱包、账户跨账本、同钱包转账、同币种换汇、负数或无效手续费均在保存前显示中文可操作错误。
- 编辑原交易时，若关联钱包已被归档或删除，禁止静默保存并提示用户选择合法钱包。
- 既有交易的商户字段为空，视作合法；关键词检索可跳过空字段。
- 新增的最近选择只保存 UUID 和账本标识，不保存余额、交易正文或敏感截图内容；失效引用必须安全忽略。

## 6. 验收标准

1. 切换账本后，首页、预算、每日记录和默认明细只展示该账本数据。
2. 切换到历史月份后，首页收支、预算进度和每日记录全部使用该月数据；未来月份不显示当前月预算或收支。
3. 任一交易可在编辑中修改所有与其类型有关的字段；成功保存后新旧钱包余额差额准确，失败时余额和原交易完全不变。
4. 新建、编辑、删除和复制交易后，首页月度收支、账户余额、预算已用金额无需重启 App 即正确刷新。
5. 明细能够组合关键词、账本、日期、金额、账户、币种、类型、分类和排序条件；组合结果稳定且无跨账本泄漏。
6. 录入页可记录商户；连续录入使用最近合法默认值；复制交易不会直接写入，必须由用户确认金额后保存。
7. 单元测试至少覆盖：多账本隔离、历史月份统计、编辑跨钱包/跨类型、替换失败回滚、删除回滚、组合筛选、最近选择失效回退。

## 7. 实施顺序

1. 建立范围与查询状态的纯模型，并先补覆盖范围一致性的测试。
2. 修复首页和明细的数据范围。
3. 引入交易草稿与统一提交路径，迁移录入和编辑页面。
4. 完成商户、最近选择与复制交易。
5. 完成明细检索、筛选、排序与筛选摘要。
6. 补端到端回归测试，验证交易、资产和预算三处同步。

此顺序保证任何可见的新能力都建立在正确账务数据之上，并让每一步都可独立验证和回退。
