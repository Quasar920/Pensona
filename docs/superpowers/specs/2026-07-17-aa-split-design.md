# AA 分摊与收款设计

日期：2026-07-17
状态：待书面审阅

## 1. 目标与范围

本功能解决单笔支出中“我先垫付”的 AA 场景：用户为一笔实际支出设置其他人数和分摊方式，App 计算个人承担与其他人合计应还，并持续记录一次或多次实际收款，直至结清。

首版坚持个人记账语义，不建设群组账本、联系人体系或在线协作能力。参与人不逐个建模，用户只填写“其他 X 人”；如需记录姓名或收款来源，使用分摊备注和每次收款备注。

## 2. 已确认的产品决策

- 仅支持“我先垫付”的支出，不支持“别人先垫付”。
- “我”始终参与分摊。
- 初始交互为“我和其他 X 人”，`X` 默认留空，由用户输入正整数。
- 分摊方式只有“AA 均分”和“自定义金额”。
- AA 均分按总人数 `1 + X` 自动计算。
- 自定义金额只输入“其他人合计应还”，系统反算“我的承担”。
- 不逐个保存参与人、姓名、份额或个人结清状态。
- 支持多次部分收款；所有收款共同冲减该笔 AA 的待收总额。
- 分摊备注和每次收款备注均可选，用户可自行填写姓名、场景或收款来源。
- 新建支出时和历史支出详情中都能发起 AA，两处共用同一个编辑器。
- 不提供催款、通讯录、分享卡片、分享文字或交互链接。
- 不支持按菜品、项目、比例或份数拆分。

## 3. 方案选择

AA 是原支出上的独立分摊能力，不复用现有“报销”语义，也不建立与交易平级的长期 AA 账单系统。

一笔原支出继续承担真实付款、账户扣减、分类和日期等账务事实；AA 只补充个人承担、其他人应还及其收回状态。这样能够给历史支出补做 AA，也不会把“从多个自己的钱包付款”的组合付款与“其他人欠我钱”的分摊混为一谈。

## 4. 账务语义

以实际支付 ¥300、我和其他 2 人均分为例：

- 原付款钱包立即减少 ¥300。
- 我的承担为 ¥100。
- 其他人合计应还为 ¥200。
- 消费统计与预算从设置 AA 起按 ¥100 计算。
- AA 待收单独显示 ¥200，不作为普通收入或可用账户余额。

收到 ¥80 后：

- 所选收款钱包增加 ¥80。
- 已收为 ¥80，待收为 ¥120。
- 普通收入仍为 ¥0。
- 原消费月份的个人消费仍为 ¥100。

钱包与总资产继续只展示真实账户余额，AA 待收作为独立信息展示，不并入可用资产。移除一笔尚未发生收款的 AA 后，该支出的消费与预算重新按实际支付全额计算。

## 5. 计算规则

### 5.1 AA 均分

输入其他人数 `X` 后：

```text
总人数 = X + 1
标准人均金额 = 按币种最小单位向下截取（实际支付金额 / 总人数）
其他人合计应还 = 标准人均金额 × X
我的承担 = 实际支付金额 - 其他人合计应还
```

除不尽的尾差由“我”承担。例如 ¥100、其他 2 人时，其他人合计应还 ¥66.66，我的承担 ¥33.34。

### 5.2 自定义金额

用户只填写其他人合计应还，系统计算：

```text
我的承担 = 实际支付金额 - 其他人合计应还
```

其他人合计应还必须大于 0 且不超过实际支付金额。其他人数在自定义模式下仍是必填信息，但不参与金额计算。

### 5.3 原支出金额变化

- 新建支出尚未保存时，AA 均分随实际支付金额和人数实时重算。
- 编辑已有支出时，AA 均分按新金额自动重算；若新的其他人应还低于累计已收，禁止保存并提示先处理收款记录。
- 自定义模式下修改原支出金额后，必须重新确认其他人合计应还；确认前不能保存。

## 6. 数据模型与组件边界

### 6.1 `AASplit`

每笔原支出最多有一条 AA 分摊，保存：

- 唯一标识；
- 原支出 ID；
- 其他人数；
- 计算方式（AA 均分或自定义金额）；
- 其他人合计应还；
- 可选备注；
- 创建与更新时间。

原支出的实际支付金额是计算输入，不在 `AASplit` 中建立第二份可编辑副本。

### 6.2 `AASettlement`

每次实际收款对应一条记录，保存：

- 唯一标识；
- 所属 AA 分摊 ID；
- 生成的收款流水 ID；
- 收款金额；
- 创建时间。

收款账户、到账日期和备注由关联收款流水保存。AA 收款流水只能从原支出的 AA 收款历史中修改或删除，不能作为普通收入独立编辑，避免分摊状态与钱包余额分叉。

### 6.3 服务职责

- `AASplitCalculator`：纯值计算，负责均分、尾差、自定义金额和差额校验。
- `AASplitService`：新增、编辑和移除 AA，校验原支出及既有收款约束。
- `AASettlementService`：原子创建或删除 AA 收款流水和关系记录，同时更新钱包余额。
- `AAQueryService`：计算单笔与全局的应收、已收、待收和状态。

SwiftUI 页面只编辑表单状态和显示查询结果，不直接修改钱包余额或拼装统计口径。

## 7. UI 与交互

页面沿用现有冷灰背景、系统蓝主交互、轻玻璃卡和至少 44 点触控区域。状态主要通过文字、轻量圆点和进度条表达，不依赖大面积红绿颜色。

### 7.1 入口

- 新建支出：在“更多信息”中增加“AA 分摊”。
- 历史支出：交易详情的更多菜单增加“发起 AA”。
- 已设置时，入口摘要显示“我和其他 X 人 · 我的承担 ¥Y”。
- 收入、转账、换汇和余额调整不显示 AA 入口。

### 7.2 AA 设置弹层

使用可向上展开的半屏弹层：

```text
取消              AA 分摊              完成

┌──────────────────────────┐
│ 本次实付                  │
│ ¥300.00                  │
└──────────────────────────┘

我和其他  [ 2 ]  人

分摊方式
┌────────────┬─────────────┐
│  AA 均分    │  自定义金额  │
└────────────┴─────────────┘

其他人合计应还              ¥200.00
我的承担                    ¥100.00

备注
┌──────────────────────────┐
│ 小王、小李；聚餐 AA        │
└──────────────────────────┘
```

- 其他人数默认留空，只接受正整数。
- AA 均分时金额只读并实时计算。
- 自定义模式只让用户编辑“其他人合计应还”。
- 输入不完整或金额非法时，错误显示在对应字段附近并禁用“完成”。
- 取消、下滑或场景中断不修改原交易和既有 AA。

### 7.3 交易详情 AA 卡片

AA 卡片位于“金额构成”之后：

```text
┌──────────────────────────┐
│ AA 分摊             待收款 │
│ 我和其他 2 人 · AA 均分    │
│                          │
│ 我的承担       ¥100.00    │
│ 已收            ¥80.00    │
│ 待收           ¥120.00    │
│ ━━━━━━━░░░░      40%      │
│                          │
│ 小王、小李；聚餐 AA         │
│                          │
│       记录收款             │
└──────────────────────────┘
```

整体状态由金额自动派生：

- 已收为 0：待收款；
- 已收大于 0 且小于应收：部分收款；
- 已收等于应收：已结清。

卡片不显示参与人列表。卡片更多菜单提供“编辑分摊”和“移除 AA”。已有收款时不能直接移除 AA。

### 7.4 记录收款弹层

```text
记录 AA 收款

剩余待收                  ¥120.00

收款金额                  ¥120.00
收款账户                  招商银行 ›
到账日期                  今天 18:30 ›
备注                      例如：小王已还

                 确认收款
```

- 金额默认等于全部剩余待收，用户可改为部分金额。
- 收款金额必须大于 0 且不得超过剩余待收。
- 收款账户仅展示原账本中与原支出币种一致的可用钱包。
- 收款历史在 AA 卡片下按到账日期倒序显示金额、钱包和可选备注。
- 删除收款需要确认，并明确说明会扣回对应钱包余额。

### 7.5 AA 待收总览

首页增加紧凑玻璃入口：

```text
AA 待收
¥320.00                         ›
共 3 笔未结清分摊
```

进入后提供“待收”和“已结清”两个状态。每项按原支出展示消费名称、日期、其他人数、计算方式、已收、待收、进度和可选备注，不展示或推断个人状态。待收列表按原支出日期倒序排列。

## 8. 数据流

### 8.1 新建支出并设置 AA

1. 用户输入支出金额、账户和分类。
2. 在“更多信息”打开 AA 设置弹层。
3. 输入其他人数，选择计算方式并可填写备注。
4. `AASplitCalculator` 产生已验证的分摊草稿。
5. 保存支出成功后，`AASplitService` 在同一提交路径中保存 AA。
6. 钱包按实际支付全额扣减；预算和消费查询按我的承担统计。

任何一步失败都不留下只有支出没有 AA、或只有 AA 没有支出的半成品。

### 8.2 为历史支出发起 AA

1. 从支出详情打开同一个 AA 设置弹层。
2. 保存前确认该交易属于当前账本、仍是合法支出且没有互斥关系。
3. 保存 AA 后，相关预算、月度消费和首页 AA 待收立即刷新。

### 8.3 记录收款

1. 从原支出 AA 卡片打开收款弹层。
2. 校验金额、账本、币种、钱包和剩余待收。
3. `AASettlementService` 创建一笔钱包流入流水及对应 `AASettlement`。
4. 钱包余额、已收、待收和状态在同一事务中更新。
5. 报表通过 AA 关系识别该流水，不将其计为普通收入。

## 9. 边界、错误与删除规则

- 仅支出可设置 AA。
- 其他人数必须为大于 0 的整数。
- 其他人应还必须大于 0 且不超过实际支付金额。
- 累计已收不得超过其他人应还。
- 已有收款后，其他人应还不能改到低于累计已收。
- 收款钱包必须和原支出属于同一账本且币种一致；首版不隐式换汇。
- 删除一条收款时，原子扣回对应收款钱包余额并恢复待收。
- 原支出没有收款时，删除原支出可同时删除 AA。
- 原支出已有收款时禁止直接删除，提示先处理 AA 收款记录。
- 已有收款时禁止直接移除 AA。
- AA 与报销互斥，避免同一金额被重复冲减。
- 首版中 AA 与退款也互斥，因为系统无法在没有参与人明细的情况下判断退款应如何分配。
- 数据库写入失败时保留用户输入，不改变钱包、AA、原交易或统计结果。
- 不存在同账本、同币种的合法收款钱包时，说明原因并禁用确认收款。

## 10. 统计、备份与同步

- 月度消费、分类统计和预算按原支出日期把“我的承担”计入原分类。
- AA 收款作为钱包流入出现在现金流水中，但明确标记为“AA 收回”，并从普通收入统计中排除。
- 首页 AA 待收等于所有未结清分摊的 `其他人应还 - 累计已收` 之和。
- AA 待收不并入钱包余额或可用总资产。
- 备份、恢复和云同步必须包含 `AASplit`、`AASettlement` 及其原支出和收款流水引用。
- 恢复前校验所有引用、账本与币种一致性；断裂引用不得静默导入。
- 新模型通过版本化 SwiftData schema 和现有恢复快照机制迁移，不改写既有交易。

## 11. 测试与验收标准

1. 实付 ¥300、其他 2 人、AA 均分时，我的承担为 ¥100，其他人应还为 ¥200。
2. 实付 ¥100、其他 2 人时，我的承担为 ¥33.34，其他人应还为 ¥66.66。
3. 实付 ¥300、自定义其他人应还 ¥180 时，我的承担为 ¥120。
4. 付款钱包原有 ¥1,000，支出后为 ¥700；收到 ¥80 后，指定收款钱包合计增加 ¥80。
5. 第 4 项场景的个人消费按 ¥100 统计，普通收入始终为 ¥0。
6. 连续收款 ¥50、¥30 后显示已收 ¥80、待收 ¥120 和“部分收款”。
7. 最后一笔收齐后状态变为“已结清”，首页待收同步减少。
8. 超额、零额、负额、跨账本和跨币种收款均不能保存，并显示字段级中文错误。
9. 已收 ¥80 后，不能把其他人应还改为低于 ¥80。
10. 删除 ¥30 收款后，对应钱包减少 ¥30，已收和待收立即恢复。
11. 删除操作在余额回滚或数据库保存失败时保持原交易、AA 和钱包不变。
12. 新建支出入口与历史支出入口使用相同计算、校验和保存结果。
13. 组合付款支出设置 AA 后，各付款钱包仍按原规则扣减，个人消费只按我的承担统计。
14. 有退款或报销关系的支出不能设置 AA；已有 AA 的支出不能新增退款或报销。
15. 备份恢复和云同步后，分摊、收款历史、钱包余额与统计结果一致。
16. VoiceOver 能读出总金额、其他人数、计算方式、我的承担、已收、待收和按钮状态；动态字体下金额与操作不截断。

## 12. 首版明确不做

- 别人先垫付或我欠别人的应付款；
- 参与人名单、联系人、个人份额和个人结清状态；
- 长期旅行、合租或群组账本；
- 按菜品、项目、比例或份数拆分；
- 催款、分享、在线确认或协作链接；
- 系统通讯录读取；
- 跨币种 AA 或收款时自动换汇；
- AA 与退款、报销同时存在；
- 把 AA 待收并入钱包余额或可用总资产。
